RPM: business-name and street-address search

Hosted address-search fallback, 11 November 2026:
- When NEXT_PUBLIC_GOOGLE_MAPS_API_KEY is absent or blank, Search uses Photon
  (OpenStreetMap data) with NZ filtering and an Auckland ranking bias.
- This replaces the unavailable Google-only search in unconfigured builds.
  Configured builds retain Google Places and Google attribution. Google runtime
  failures do not silently send the query to another provider.
- Lookup runs only on Search/Enter, never on typing. Requests are serialized
  and spaced in the browser, with a bounded session cache. Photon is a public
  fair-use service, not a guaranteed geocoding SLA; see
  https://github.com/komoot/photon#demo-server.
- OpenStreetMap results show attribution and retain their coordinates on save
  so the existing Leaflet map can display them. They have no Google place ID.
  Overseas/invalid coordinates are discarded; street-only results cannot be
  selected as complete addresses. Manual entry remains available.
- No hosting settings, API keys, database migrations or existing-site edits
  are required for this fallback. Google business coverage still requires the
  Google configuration described below.

Configuration before a staging test
1. Use a Google Cloud project with billing enabled, Maps JavaScript API and
   Places API (New) enabled. Set quotas/budget alerts as appropriate.
2. Create a browser API key restricted to the intended HTTP referrers (including
   localhost for local testing) and only those two APIs. Do not use a server or
   unrestricted key. NEXT_PUBLIC_GOOGLE_MAPS_API_KEY is deliberately public.
3. Set NEXT_PUBLIC_GOOGLE_MAPS_API_KEY and NEXT_PUBLIC_GOOGLE_MAPS_MAP_ID before
   building. Use a JavaScript map ID for production; DEMO_MAP_ID is the local
   fallback. See .env.example. Existing Supabase configuration is also required.
4. Apply the additive add_store_address_details migration to a disposable/local
   or approved staging database, using the normal migration process. It adds one
   nullable JSONB column, with no backfill, UPDATE, trigger, scheduled job or RLS
   change. Do not apply it to production without approval.
5. Review RPM's public terms/privacy disclosures for Google Maps/Places use.

Behavior
- Site Address accepts a business/site name or street address. Search (or Enter)
  explicitly submits the query; there is no background per-keystroke billing.
- Results show business name, formatted street address and locality. Auckland is
  the ranking bias; returned addresses must have an NZ country component.
- Selecting a result captures structured address fields and a Google place ID.
  Save confirms the address as site data. An unselected search query cannot be
  saved as a street address.
- Google-linked sites persist the place ID rather than a permanent coordinate
  cache. The Google map retrieves coordinates when displaying the site. This is
  an intentional adjustment to the request to save coordinates: map pins survive
  reopening without storing Google's coordinates indefinitely.
- Existing lat/lng values are preserved for legacy/manual sites. Opening the
  modal, changing search mode or viewing the map does not write site records.
  Only an explicit save inserts a site or updates the selected site's ID.
- Editing address text clears the previous location. Manual mode permits an
  unlisted premise's full address; it has no pin until a matching location is
  selected. Switching mode alone preserves an unchanged existing address/pin.
- With a Google key configured, Sites uses a Google map, retaining status colors,
  current client brands, health traffic lights, public primary/recent photo,
  site link, NZ bounds and reset control. Internal-only photos remain excluded.
  The missing-pin filter and location badges recognize Google place IDs.
  Without a key, the legacy map
  remains for pre-existing locations; Google-derived sites are excluded from it.
- Search errors/empty results keep manual entry available. Editing/unmounting
  invalidates late search responses.
